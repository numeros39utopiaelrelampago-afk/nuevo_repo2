¿Qué es Git?

Git es un sistema de control de versiones distribuido. Permite registrar el historial de cambios de cualquier conjunto de archivos, coordinar el trabajo entre múltiples personas y volver a cualquier estado anterior del proyecto.

Fue creado en 2005 por Linus Torvalds (el creador de Linux) para gestionar el kernel de Linux. Hoy es el estándar de facto en la industria del software.

¿Para qué sirve?

  • Guardar el historial completo de cambios de un proyecto.
  • Trabajar en paralelo con ramas sin pisar el trabajo ajeno.
  • Colaborar con equipos distribuidos (GitHub, GitLab, Bitbucket).
  • Revertir errores a un estado anterior conocido.
  • Comparar versiones de archivos en el tiempo.

Git vs GitHub

Git es la herramienta local que gestiona el historial. GitHub es una plataforma en la nube que aloja repositorios Git y agrega funcionalidades de colaboración (pull requests, issues, etc.). Git funciona sin GitHub, pero GitHub requiere Git.

Configuración inicial

git config Configurar nombre, email y preferencias globales

La configuración se aplica a nivel --global (todos los repos del usuario) o local (solo el repo actual).

Configuración mínima obligatoria:

git config --global user.name "Tu Nombre"
git config --global user.email "tu@email.com"

Otras configuraciones útiles:

# Editor por defecto (Visual Studio Code):
git config --global core.editor "code --wait"

# Que la rama principal se llame 'main' en repos nuevos:
git config --global init.defaultBranch main

# Colores en la terminal:
git config --global color.ui auto

# Ver toda la configuración:
git config --list

# Ver un valor específico:
git config user.email
VarianteDescripción
git config --globalAfecta a todos los repos del usuario actual.
git config --localSolo afecta al repo actual (valor por defecto si no se especifica).
git config --systemAfecta a todos los usuarios de la máquina (requiere admin).
git config --listMuestra toda la configuración activa.
git config --unset <clave>Elimina una configuración.
✓ Salida esperada (éxito)
Ningún output. Si querés verificar: git config user.name devuelve tu nombre.

Errores comunes:

error: could not lock config file ... : Permission denied
Causa: El archivo de configuración está siendo usado por otro proceso o no tenés permisos.
Solución: Cerrar otras terminales o ejecutar sin --system. En Linux/Mac verificar permisos con ls -la ~/.gitconfig.
Author identity unknown *** Please tell me who you are.
Causa: No configuraste nombre y email antes de hacer el primer commit.
Solución: Ejecutar git config --global user.name "..." y git config --global user.email "...".

  3. Configurá tu email: git config --global user.email "tu-email@ejemplo.com"
  4. Verificá con: git config --list

Inicio de repositorios

git init Crear un nuevo repositorio Git local

Transforma una carpeta normal en un repositorio Git. Crea una carpeta oculta .git/ donde Git almacena todo el historial.

# Inicializar en la carpeta actual:
git init

# Crear e inicializar una nueva carpeta:
git init nombre-del-proyecto

# Especificar la rama inicial:
git init --initial-branch=main
# (equivalente abreviado):
git init -b main
✓ Salida esperada
Initialized empty Git repository in C:/Users/tuusuario/mi-proyecto/.git/

Errores comunes:

Reinitialized existing Git repository in .../mi-proyecto/.git/
No es un error grave, solo un aviso de que ya existía un repo.
Solución: Si fue intencional, ignorar. Si no, verificar que estás en la carpeta correcta con pwd.
'git init' existe solo como subcomando de otro comando
Causa: Git no está correctamente instalado o no está en el PATH.
Solución: Reinstalar Git y abrir una nueva terminal.
git clone Copiar un repositorio remoto a tu máquina

Descarga una copia completa de un repositorio (con todo su historial) desde un servidor remoto.

# Clonar en una carpeta con el nombre del repo:
git clone https://github.com/usuario/repositorio.git

# Clonar en una carpeta con nombre personalizado:
git clone https://github.com/usuario/repositorio.git mi-carpeta

# Clonar una rama específica:
git clone -b nombre-rama https://github.com/usuario/repo.git

# Clonar con SSH (requiere clave SSH configurada):
git clone git@github.com:usuario/repositorio.git

# Clonar solo el último commit (más rápido para repos grandes):
git clone --depth=1 https://github.com/usuario/repo.git
✓ Salida esperada
Cloning into 'repositorio'...
remote: Enumerating objects: 45, done.
remote: Counting objects: 100% (45/45), done.
remote: Compressing objects: 100% (30/30), done.
Receiving objects: 100% (45/45), 12.34 KiB | 1.23 MiB/s, done.

Errores comunes:

fatal: repository 'https://github.com/...' not found
Causa: La URL es incorrecta, el repo es privado y no estás autenticado, o el repo fue borrado.
Solución: Verificar la URL. Si es privado, autenticarse primero: gh auth login (GitHub CLI) o configurar token de acceso personal.
fatal: destination path 'nombre' already exists and is not an empty directory.
Causa: Ya existe una carpeta con ese nombre en el directorio actual.
Solución: Borrar la carpeta existente o clonar con otro nombre: git clone URL otro-nombre
error: SSL certificate problem: unable to get local issuer certificate
Causa: Problema con los certificados SSL (común en redes corporativas o universitarias con proxy).
Solución temporal: git config --global http.sslVerify false (solo para pruebas, no en producción).
Permission denied (publickey)
Causa: Intentaste clonar via SSH pero no tenés una clave SSH configurada o no la agregaste a GitHub.
Solución: Usá HTTPS en vez de SSH, o generá una clave: ssh-keygen -t ed25519 -C "tu@email.com" y agregala a GitHub en Settings → SSH keys.

Inspección del repositorio

git status Ver el estado actual del repositorio

Muestra qué archivos fueron modificados, cuáles están en el staging area y cuáles no están siendo rastreados por Git. Es el comando más usado del día a día.

# Estado completo (más legible):
git status

# Estado compacto (una línea por archivo):
git status -s
git status --short

# Incluye archivos ignorados:
git status --ignored

Posibles salidas:

git log Ver el historial de commits

Muestra el historial de commits del repositorio, del más reciente al más antiguo.

# Historial completo:
git log

# Una línea por commit (más compacto):
git log --oneline

# Con gráfico de ramas:
git log --oneline --graph --all

# Últimos N commits:
git log -5

# Commits de un archivo específico:
git log -- archivo.txt

# Buscar commits por mensaje:
git log --grep="fix"

# Commits entre fechas:
git log --after="2024-01-01" --before="2024-12-31"

# Commits de un autor:
git log --author="Nombre"

# Formato personalizado:
git log --pretty=format:"%h | %an | %ar | %s"
✓ Salida esperada (git log --oneline)
a3f2b1c (HEAD -> main, origin/main) Agregar README con instrucciones
7e9d2a1 Crear estructura de carpetas inicial
3c8f401 Initial commit

Navegar el log largo:

⚠ La terminal se queda "colgada"
git log usa un pager (el programa less). Para navegar: ↑↓ o Space para avanzar. Para salir: presionar Q.
fatal: your current branch 'main' does not have any commits yet
Causa: El repo fue inicializado con git init pero no tiene ningún commit todavía.
Solución: Crear al menos un commit primero: agregar un archivo y hacer git add . && git commit -m "Initial commit".
git diff Ver cambios entre versiones de archivos

Muestra exactamente qué líneas cambiaron. Las líneas en rojo con - fueron quitadas; las verdes con + fueron agregadas.

# Cambios en working dir (no en staging):
git diff

# Cambios que ya están en staging:
git diff --staged
git diff --cached

# Diferencia entre dos commits:
git diff abc1234 def5678

# Diferencia entre dos ramas:
git diff main feature/login

# Solo los nombres de archivos que cambiaron:
git diff --name-only

# Diferencia de un archivo específico:
git diff index.html
✓ Salida esperada
diff --git a/index.html b/index.html
index 1a2b3c4..5d6e7f8 100644
--- a/index.html
+++ b/index.html
@@ -10,7 +10,8 @@
   <body>
-    <h1>Título viejo</h1>
+    <h1>Título nuevo</h1>
+    <p>Párrafo agregado</p>
   </body>
(no output)
Causa frecuente: Si no hay output, puede que los cambios ya estén en staging. En ese caso git diff no muestra nada.
Solución: Usar git diff --staged para ver los cambios que ya pasaron por git add.
git show Inspeccionar un commit específico 
# Ver el último commit (HEAD):
git show

# Ver un commit específico:
git show a3f2b1c

# Ver solo el mensaje del commit:
git show --stat a3f2b1c

# Ver el contenido de un archivo en ese commit:
git show a3f2b1c:archivo.txt

Staging y Commits

git add Agregar cambios al staging area

Mueve cambios del working directory al staging area. Solo los cambios en staging se incluirán en el próximo commit.

# Agregar un archivo específico:
git add archivo.txt

# Agregar múltiples archivos:
git add archivo1.txt archivo2.txt

# Agregar todos los archivos del directorio actual:
git add .

# Agregar todos los archivos del repositorio:
git add -A

# Agregar archivos por extensión:
git add *.html

# Modo interactivo (elegir línea por línea):
git add -p
✓ Sin output = éxito
git add no muestra nada si funcionó. Verificar con git status.

Errores comunes:

fatal: pathspec 'archivo.txt' did not match any files
Causa: El archivo no existe con ese nombre o estás en la carpeta equivocada.
Solución: Verificar con ls que el archivo existe. Cuidado con mayúsculas y extensiones.
warning: LF will be replaced by CRLF in archivo.txt
Causa: El archivo usa saltos de línea Unix (LF) pero Git lo convertirá al estilo Windows (CRLF).
No es un error. Para evitar el warning: git config --global core.autocrlf true (Windows) o false (Linux/Mac).
🎯 Ejercicio 3 — Crear y agregar tu archivo
  1. Dentro del repo, crear la carpeta de alumnos si no existe: mkdir alumnos
  2. Crear tu archivo: echo "Hola, soy [Tu Nombre]" > alumnos/[tu-nombre].txt
  3. Ver el estado: git status (vas a ver el archivo como "untracked")
  4. Agregar al staging: git add alumnos/[tu-nombre].txt
  5. Ver el estado de nuevo: git status (ahora está en verde como "new file")
git commit Guardar los cambios del staging como un commit

Crea una instantánea permanente de los cambios en staging. Cada commit tiene un hash único, autor, fecha y mensaje.

# Commit con mensaje:
git commit -m "Agregar archivo de bienvenida"

# Commit con mensaje multilínea:
git commit -m "Título del commit" -m "Descripción más detallada"

# Agregar todos los cambios modificados y hacer commit (sin git add):
git commit -am "Mensaje"

# Modificar el ÚLTIMO commit (antes de hacer push):
git commit --amend -m "Mensaje corregido"

# Commit vacío (útil para disparar CI/CD):
git commit --allow-empty -m "Trigger CI"
✓ Salida esperada
[main a3f2b1c] Agregar mi archivo de alumno
 1 file changed, 1 insertion(+)
 create mode 100644 alumnos/juan-perez.txt

Buenas prácticas para mensajes de commit:

  • Usar verbos en infinitivo o imperativo: "Agregar", "Corregir", "Eliminar".
  • Máximo 72 caracteres en la primera línea.
  • Describir qué y por qué, no cómo.
  • Ejemplos: "Agregar validación de email en registro", "Corregir bug en cálculo de total con descuento"

Errores comunes:

On branch main nothing to commit, working tree clean
Causa: No hay cambios en el staging area.
Solución: Primero hacer git add con los archivos a incluir.
Aborting commit due to empty commit message.
Causa: Se abrió el editor para escribir el mensaje pero se cerró sin escribir nada.
Solución: Siempre usar -m "mensaje" para evitar que se abra el editor, o escribir el mensaje antes de cerrar el editor.
error: gpg failed to sign the data
Causa: Git está configurado para firmar commits con GPG pero la clave no está disponible.
Solución: Deshabilitar firma GPG: git config --global commit.gpgsign false
🎯 Ejercicio 4 — Hacer tu primer commit
  1. Verificar que tu archivo está en staging: git status
  2. Hacer el commit: git commit -m "Agregar archivo de alumno [Tu Nombre]"
  3. Ver que el commit quedó registrado: git log --oneline
  4. Ver los detalles del último commit: git show
git restore Descartar cambios en archivos individuales

Descarta cambios en archivos del working directory o saca archivos del staging (sin afectar el historial).

# Descartar cambios en un archivo (volver al último commit):
git restore archivo.txt

# Sacar un archivo del staging (no elimina los cambios, solo los "destagea"):
git restore --staged archivo.txt

# Restaurar todos los archivos modificados:
git restore .

# Restaurar a una versión de un commit específico:
git restore --source=a3f2b1c archivo.txt
⚠ Advertencia importante
git restore archivo.txt elimina permanentemente los cambios del working directory. No se puede deshacer. Usarlo con cuidado.

Ramas (Branches)

git branch Crear, listar y eliminar ramas

Las ramas permiten trabajar en paralelo sin afectar el código principal. La rama principal se suele llamar main (antes master).

# Ver todas las ramas locales:
git branch

# Ver ramas locales y remotas:
git branch -a

# Crear una rama nueva:
git branch feature/login

# Eliminar una rama (solo si ya fue mergeada):
git branch -d feature/login

# Forzar eliminación (aunque no fue mergeada):
git branch -D feature/login

# Renombrar la rama actual:
git branch -m nuevo-nombre

# Ver qué ramas ya fueron mergeadas a main:
git branch --merged main
✓ Salida de git branch
  develop
* main
  feature/login
El * indica la rama donde estás actualmente.
error: A branch named 'feature/login' already exists.
Causa: Ya existe una rama con ese nombre.
Solución: Usar otro nombre o eliminar la rama existente primero.
error: The branch 'feature/login' is not fully merged.
Causa: La rama tiene commits que no fueron incorporados a otra rama.
Solución: Hacer merge primero, o usar git branch -D si estás seguro de querer eliminarla de todos modos.
🎯 Ejercicio 5 — Crear tu rama de trabajo
  1. Ver las ramas existentes: git branch -a
  2. Crear tu propia rama: git branch feature/[tu-nombre]
  3. Verificar que se creó: git branch
  4. Moverse a esa rama (siguiente sección: git switch).
git switch Cambiar de rama (reemplaza git checkout para ramas)

git switch fue introducido en Git 2.23 para hacer más clara la función de cambiar de rama. git checkout sigue funcionando pero hace muchas cosas a la vez.

# Ir a una rama existente:
git switch main
git switch feature/login

# Crear y moverse a una nueva rama (shortcut):
git switch -c feature/nueva-funcionalidad

# Volver a la rama anterior:
git switch -

# Equivalentes con git checkout (más antiguo, aún válido):
git checkout main
git checkout -b feature/nueva-funcionalidad
✓ Salida esperada
Switched to branch 'feature/login'
o si se crea nueva: 
Switched to a new branch 'feature/nueva-funcionalidad'

Errores comunes:

error: Your local changes to the following files would be overwritten by checkout: archivo.txt Please commit your changes or stash them before you switch branches.
Causa: Tenés cambios sin commitear en archivos que también existen en la otra rama.
Solución: Hacer commit: git commit -am "WIP", o guardar temporalmente con git stash, cambiar de rama, y luego recuperar: git stash pop.
fatal: 'feature/login' is not a branch.
Causa: La rama no existe localmente.
Solución: Si la rama está en el remoto, usar: git switch feature/login (Git la busca automáticamente en remoto) o git fetch && git switch feature/login.
🎯 Ejercicio 6 — Moverse a tu rama y trabajar en ella
  1. Moverse a tu rama: git switch feature/[tu-nombre]
  2. Verificar que estás ahí: git branch (el * debe apuntar a tu rama)
  3. Modificar tu archivo: agregar una línea de texto
  4. Hacer add y commit: git add . && git commit -m "Actualizar mi archivo en mi rama"
  5. Ver el log: git log --oneline
git merge Combinar una rama en la rama actual

Incorpora los cambios de otra rama en la rama donde estás. Git crea un "merge commit" si las ramas divergieron.

# Primero ir a la rama destino (donde querés traer los cambios):
git switch main

# Luego hacer merge de la otra rama:
git merge feature/login

# Merge sin crear merge commit (fast-forward only):
git merge --ff-only feature/login

# Merge siempre creando merge commit (aunque se pueda fast-forward):
git merge --no-ff feature/login -m "Merge feature/login into main"

# Abortar un merge en progreso (cuando hay conflictos):
git merge --abort
✓ Merge exitoso (fast-forward)
Updating a3f2b1c..7e9d2a1
Fast-forward
 alumnos/juan-perez.txt | 2 ++
 1 file changed, 2 insertions(+)
✓ Merge exitoso (con merge commit)
Merge made by the 'ort' strategy.
 feature.txt | 5 +++++
 1 file changed, 5 insertions(+)

Resolver conflictos de merge:

✗ Conflicto de merge
Auto-merging archivo.txt
CONFLICT (content): Merge conflict in archivo.txt
Automatic merge failed; fix conflicts and then commit the result.

Cuando hay un conflicto, Git marca el archivo así:

# Contenido del archivo con conflicto:
<<<<<<< HEAD
Esta es mi versión (rama actual)
=======
Esta es la versión de la otra rama
>>>>>>> feature/login

Para resolver:

  1. Abrir el archivo y editar manualmente, quedarse con el contenido correcto (borrar las marcas <<<, ===, >>>).
  2. git add archivo.txt
  3. git commit -m "Resolver conflicto en archivo.txt"
💡 Consejo
Usar un editor como VS Code facilita mucho la resolución de conflictos: muestra botones para "Accept Current Change", "Accept Incoming Change" o "Accept Both Changes".
🎯 Ejercicio 7 — Merge de tu rama a main
  1. Volver a la rama principal: git switch main
  2. Hacer merge de tu rama: git merge feature/[tu-nombre]
  3. Ver el historial con gráfico: git log --oneline --graph
  4. Si hay conflictos: editar el archivo, git add . y git commit
git rebase Reorganizar commits sobre otra base

Rebase mueve o "replanta" los commits de una rama sobre otra, creando un historial más lineal. A diferencia de merge, reescribe el historial.

# Hacer rebase de la rama actual sobre main:
git rebase main

# Rebase interactivo (reorganizar, editar o unir commits):
git rebase -i HEAD~3    # Últimos 3 commits

# Continuar un rebase después de resolver conflictos:
git rebase --continue

# Abortar un rebase en progreso:
git rebase --abort

# Saltear un commit con conflicto:
git rebase --skip
⚠ Regla de oro del rebase
Nunca hacer rebase en ramas que ya fueron pusheadas y que otras personas usan. Rebase reescribe el historial, lo que causa problemas graves a los demás.

Rebase vs Merge:

Característicamergerebase
HistorialPreserva todo (con merge commit)Lineal (reescribe commits)
Seguridad en ramas públicasSeguro siemprePeligroso si ya fue pusheado
Uso recomendadoIntegrar features en mainActualizar feature branch con main

git remote Gestionar repositorios remotos

git fetch Descargar cambios del remoto sin aplicarlos

Descarga los cambios del servidor remoto pero no modifica tu working directory ni tus ramas locales. Es una operación segura para "ver qué hay de nuevo".

# Traer todos los cambios de origin:
git fetch

# Traer de un remoto específico:
git fetch origin

# Traer una rama específica:
git fetch origin main

# Traer todos los remotos:
git fetch --all

# Ver qué cambió después del fetch:
git log HEAD..origin/main --oneline
git pull Descargar y aplicar cambios del remoto

git pull = git fetch + git merge (o git rebase). Descarga y aplica los cambios del remoto en la rama local.

# Pull de la rama actual desde origin:
git pull

# Pull de una rama específica:
git pull origin main

# Pull con rebase en lugar de merge:
git pull --rebase

# Pull forzando fast-forward (falla si hay divergencia):
git pull --ff-only

Deshacer cambios

git stash Guardar cambios temporalmente sin hacer commit

Guarda los cambios actuales (working dir y staging) en una pila temporal para que puedas cambiar de rama sin commitear trabajo incompleto.

# Guardar cambios actuales:
git stash

# Guardar con descripción:
git stash push -m "WIP: agregar validación de login"

# Ver lista de stashes guardados:
git stash list

# Recuperar el último stash (y eliminarlo de la pila):
git stash pop

# Recuperar un stash específico:
git stash pop stash@{2}

# Aplicar sin eliminar de la pila:
git stash apply stash@{0}

# Eliminar el último stash:
git stash drop

# Eliminar todos los stashes:
git stash clear

# Ver el contenido de un stash:
git stash show -p stash@{0}

Saved working directory and index state WIP on main: a3f2b1c Último commit
No local changes to save
Causa: No hay cambios en el working directory o staging.
No hay nada que guardar. Verificar con git status.
error: Your local changes to the following files would be overwritten by merge
Causa: Hiciste pop del stash y hay conflicto con cambios actuales.
Solución: Primero commitear o descartar los cambios actuales, luego hacer el pop.
🎯 Ejercicio 10 — Guardar trabajo a medias
  1. Hacer un cambio en un archivo sin commitear.
  2. Guardar con: git stash push -m "Cambio en progreso"
  3. Ver que el working dir quedó limpio: git status
  4. Ver la lista: git stash list
  5. Recuperar los cambios: git stash pop
  6. Verificar que los cambios volvieron: git status
git reset Mover HEAD y deshacer commits (modifica el historial)

Mueve el puntero HEAD a un commit anterior. Tiene tres modos según qué pasa con los archivos.

# SOFT: deshace el commit, los cambios quedan en staging:
git reset --soft HEAD~1

# MIXED (defecto): deshace el commit y el staging, cambios en working dir:
git reset HEAD~1
git reset --mixed HEAD~1

# HARD: deshace commit, staging Y working dir. ¡PELIGROSO, se pierden cambios!
git reset --hard HEAD~1

# Volver a un commit específico:
git reset --hard a3f2b1c

# Sacar un archivo del staging (sin afectar working dir):
git reset HEAD archivo.txt    # equivale a git restore --staged

Diferencias entre los modos:

ModoCommitStagingWorking Dir
--softDeshaceConserva cambiosConserva cambios
--mixedDeshaceLimpiaConserva cambios
--hardDeshaceLimpiaElimina cambios
⚠ Usar con precaución
git reset reescribe el historial. Nunca usarlo en commits que ya fueron pusheados a una rama compartida. Si necesitás deshacer un commit público, usar git revert.
fatal: ambiguous argument 'HEAD~1': unknown revision
Causa: El repo tiene menos commits de los que intentás retroceder.
Solución: Ver cuántos commits hay con git log --oneline y ajustar el número.
🎯 Ejercicio 11 — Deshacer un commit local
  1. Hacer un commit "de prueba": git commit --allow-empty -m "Commit de prueba"
  2. Ver que aparece en el log: git log --oneline -3
  3. Deshacer ese commit: git reset --soft HEAD~1
  4. Ver que el commit desapareció pero los cambios siguen: git log --oneline -3 y git status
git revert Deshacer un commit creando uno nuevo (seguro para ramas públicas)

Crea un commit nuevo que deshace los cambios de un commit anterior. No reescribe el historial, por eso es seguro usarlo en ramas compartidas.

# Revertir el último commit:
git revert HEAD

# Revertir un commit específico:
git revert a3f2b1c

# Revertir sin abrir el editor (mensaje automático):
git revert HEAD --no-edit

# Revertir múltiples commits:
git revert HEAD~3..HEAD

# Preparar el revert sin commitear todavía:
git revert -n HEAD
✓ Salida esperada
[main 7f2a1b3] Revert "Agregar funcionalidad X"
 1 file changed, 5 deletions(-)

Solución: Resolver los conflictos manualmente, hacer git add . y luego git revert --continue.
🎯 Ejercicio 12 — Revertir un commit ya pusheado
  1. Hacer un cambio malo, commitearlo y pushearlo: git commit -am "Cambio incorrecto" && git push
  2. Ver el hash del commit a revertir: git log --oneline -3
  3. Revertir: git revert HEAD --no-edit
  4. Pushear el revert: git push
  5. Ver el historial: git log --oneline -5 (el commit original sigue, hay uno nuevo que lo deshace)

git tag

# Crear tag anotado (con mensaje, recomendado para releases):

git cherry-pick Aplicar un commit específico de otra rama

Copia un commit de otra rama y lo aplica en la rama actual. Útil cuando querés traer un fix específico sin mergear toda la rama.

# Aplicar un commit:
git cherry-pick a3f2b1c

# Aplicar múltiples commits:
git cherry-pick a3f2b1c 7e9d2a1

# Aplicar sin crear commit automáticamente:
git cherry-pick -n a3f2b1c

# Continuar después de resolver conflictos:
git cherry-pick --continue

# Abortar:
git cherry-pick --abort
git reflog Historial de movimientos de HEAD (la "red de seguridad")

Registra todos los movimientos de HEAD, incluso los de git reset --hard. Sirve para recuperar commits "perdidos".

# Ver el historial completo de movimientos:
git reflog

# Recuperar un commit "borrado" con reset --hard:
git reflog
# Encontrás el hash del commit que querés recuperar, por ejemplo: a3f2b1c
git reset --hard a3f2b1c
✓ Salida esperada
a3f2b1c (HEAD -> main) HEAD@{0}: reset: moving to HEAD~1
9b7c2d4 HEAD@{1}: commit: Cambio que "borramos"
a3f2b1c HEAD@{2}: commit: Commit anterior
💡 Dato clave
El reflog solo existe localmente y por defecto se limpia después de 90 días. Es tu red de seguridad ante git reset --hard accidentales.
.gitignore Indicar a Git qué archivos ignorar

Un archivo de texto llamado .gitignore en la raíz del repo. Cada línea es un patrón de archivos o carpetas que Git ignorará por completo.

# Archivos compilados / build

desktop.ini

# IDEs y editores
.vscode/
.idea/
*.swp
*.swo

# Logs
*.log

# Ignorar todos los .txt excepto uno:

Sintaxis del .gitignore:

PatrónDescripción

node_modules/La carpeta node_modules y todo su contenido

docs/*.mdArchivos .md dentro de docs/ (no en subdirectorios)
!archivo.txtExcepción: NO ignorar este archivo
# comentarioLínea de comentario, ignorada por Git
El archivo aparece en git status aunque lo agregué al .gitignore
Causa: El archivo ya estaba siendo rastreado por Git antes de agregarlo al .gitignore.
Solución: Dejar de rastrear el archivo sin borrarlo del disco: git rm --cached archivo.txt, luego commitear el cambio.

Flujo de trabajo colaborativo

Este es el flujo típico para trabajar en equipo con Git y GitHub:

1. git clone URL — Clonar el repo una sola vez
↓
2. git switch -c feature/mi-tarea — Crear rama para tu tarea
↓
3. Trabajar: editar archivos, probar...
↓
4. git add . → git commit -m "..." — Commitear cambios
↓
5. git pull origin main — Traer últimos cambios de main
↓
6. Resolver conflictos si los hay
↓
7. git push -u origin feature/mi-tarea — Subir tu rama
↓
8. Abrir Pull Request en GitHub para revisión
↓
9. Revisión + merge del Pull Request por el líder
↓
10. git switch main → git pull → repetir desde el paso 2
